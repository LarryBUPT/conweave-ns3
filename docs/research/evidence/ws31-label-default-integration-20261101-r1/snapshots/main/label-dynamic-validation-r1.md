## 3. 逐包与机制验收

按 uid 将每次构包与各跳实际标签观测及 ROUTE 对应，核对构包／原需求时刻、四元组、序号、载荷、flow_id、原标签、实际值及存在性。重传按当次 uid 对应，原业务真值不改。全部请求、字节、队列、时刻和路径保持须通过。

C1 重放实际首次模板、预测账、区间扣减、懒到期和 Q+R 选择，后续变标签不得重登记预算。C3 重放首次缓存类别、活动、候选、配额、借用和残留，后续标签不能迁移旧 QP。C1 末态可能保留尚未用尽的预测条目，不能由汇总强行清零。

C2 在原需求时刻只采样一次。profile 1 全部立即放行；profile 2 的六个原类别 2 请求总等待 1,588 ns、最大 413 ns；profile 3 的正等待为六个，总等待 1,457 ns、最大 409 ns。原需求 FCT 包含等待，未知标签立即放行。上述数值由冻结四元组哈希推得，不是收益目标。

profile 1 的 C2／C3 完整 FCT 和路径须恢复本轮 QueuePin 参考。路径比较只去 uid 和刻意变化的 tag，实际标签及存在性另逐条核对。C1 未知模板仍可能改变决策，使用精确账本验收，不要求其等于 QueuePin。
