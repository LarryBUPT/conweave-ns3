# C2 有界启动分散实现契约

日期：2026 年 11 月 1 日。判断：实现并进入正确性验证；收益、类别增量和贡献范围均待独立实验判断。

## 1. 决策与信息边界

仅在应用请求已经到达时计算等待。固定四元组哈希生成闭区间 `[0, 500] ns` 的偏移；不消耗模拟器随机数，不读取后续输入、完成结果或批次尾部。500 ns 是本版本的工程初值，未经效果校准。未来若校准，须先冻结独立协议。

模式 43（`ws31-c2`）仅对 tag 2 请求分散，未知标签、tag 1 立即放行；44（`ws31-c2-unified`）对所有请求分散；45（`ws31-c2-size`）仅对 8,192 B 请求分散；46（`ws31-c2-zero`）全部零等待。只有模式 45 的资格判断读取大小。四个模式均沿原 QueuePin 选路，不叠加 C1。

## 2. 时间与生命周期

原 trace 不改动。`RdmaClient::StartApplication` 记录需求时刻，非零等待安排独立放行事件，零等待直接调用放行函数。待放行请求在 Stop/Dispose 时取消，计入取消数和字节，不能计作已经完成。

需求时刻经 `RdmaDriver` 传到 `RdmaHw`。QP 在实际放行时创建，拥塞控制仍在此时初始化；只将统计起点 `startTime` 设为原需求时刻，并单独保存启动等待。现有 FCT 八列格式保持，起点是需求，FCT 包含等待。其他模式采用默认未指定起点参数，保持原行为。

## 3. 观测与守恒

模式专属汇总记录需求、放行、取消、完成的请求数与字节，待放行和未完成数，以及等待总和与最大值。技术观测开启时，逐流输出需求、放行与完成时刻，便于按 flow ID 检查身份、时间顺序和 raw FCT。观测数据不回流到决策。

未完成请求不能从尾部统计中静默消失。完整端到端验收要求需求与输入一致、无意外取消或待放行、完成数和字节守恒；若终止时仍有请求，则保留并报告，不仅计算已完成流分位数。

## 4. 必须完成的验证

核心验证覆盖确定性、闭区间边界、零等待、类别未知回退、类别／大小控制等价以及统一控制。后续 ns-3 验证包括完整构建、零等待相对 QueuePin 的 raw 回归、需求／放行／完成时间核对、标签干预、Stop/Dispose 取消，以及无丢失和字节守恒。核心测试不代表这些端到端验收已通过。

效果判断必须从原需求时刻计算业务批次与背景 FCT，分别比较通用错峰、大小错峰和类别错峰。等待抵消收益、背景恶化或通用控制已解释效果时，保留负结果；不从效果数据反复搜索偏移上限。
