## 2. 拟实现的独立标签夹具

新增默认关闭的独立测试配置，不复用旧控制器。原业务标签、大小、四元组和需求起点始终保持。夹具只决定决策时可见标签及包上携带的标签；与已有全量标签变换同时开启时拒绝执行。

| 配置 | 原需求时刻的可见标签 | 后续数据包标签 | 必验结果 |
| --- | --- | --- | --- |
| 默认 0 | 原标签 | 原标签 | 与固定 506 源的匹配输入恢复一致 |
| 延迟可得 1 | 未知 0，标签缺失 | 原需求后不足 500 ns 时缺失；达到 500 ns 后为原标签且标签存在 | C1／C3 按首次实际收到包的标签确定首次策略；后续可得不迁移、不重新登记预算。C2 立即放行，不追补等待 |
| 后续改变 2 | 原标签 | 前 500 ns 为原标签；其后已知 1／2 互换 | C1 模板和 C3 活动身份沿首次实际包类别；C2 按原需求时刻资格只计算一次等待 |
| 部分错误 3 | 固定四元组哈希的四个桶中，桶 0 的已知类别互换 1／2 | 同一请求持续使用该决定 | 原业务分组保持；错误与正确请求均出现，实际决定逐项重放 |

500 ns 是为覆盖决策前后变化而指定的技术时刻，沿用当前 C2 等待上界的量级，不作参数搜索。它不表示真实应用能在 500 ns 内分类。部分错误是合成干预。一个桶的命中率约为四分之一，小输入不保证恰有四分之一请求。

时间依据为原需求时刻，不是 QP 创建后重新计时。包标签在发送构造时决定；不能把源交换机收到包的时刻当作标签生成时刻。重传按当次构造时刻取标签，验收必须据真实包对应关系检查。

技术观测记录生成时刻、原需求时刻、四元组、序号、载荷、包 uid、flow_id、原标签、可见标签及标签存在性。每跳另读真实 PacketTag 的 present，不能从构包日志单独推断标签仍在。小输入允许逐包日志，以便和源 ROUTE 逐一对应。记录不回流到策略，不能只记录最终汇总来推断标签变化。

## 6. 审查修订的精确定义

用于证明“首次未知后可得”或“首次已知后改变”的目标请求，必须实际观察到阈值前首次构包和阈值后构包。若首次构包已晚于 500 ns，就按该包的实际标签验收，但不能计入前后变化的覆盖数。判定时点不能从 NIC 负载或请求到达时刻推测。

profile 1 在阈值前返回 `present=false,value=0`，阈值后返回 `present=true,value=original`。显式原标签 0 也保留存在性差别。profile 2 的未知标签 0、7、99 原样保留。

profile 3 固定采用现有 `StartHash`：三字依次为 sip、dip、`sport | (dport << 16)`；逐字按低字节在前处理。FNV 初值为 `2166136261 ^ 0x43c2a517`，乘数 16777619，32 位回绕，再执行固定尾混合。只选择 `hash & 3 == 0` 的桶，已知 1／2 互换。重复及同四元组重新创建保持同桶；待输入冻结时列实际四元组和两类选择数，先保证两类都包含错误／正确请求。

C2 仍在原需求时刻只采样一次标签；默认 0 路径保持旧 transform 语义。启用时限定 WS-31 模式、明确的 ws31 输入、完整观测及共同传输条件，并拒绝旧 composition／lifecycle／transform／故障配置。worker 明确写入 `WS31_LABEL_PROFILE=0` 清除继承环境。

本标签子阶段明确 `generation=0`、每个请求有唯一 flow_id。同四元组重建夹具尚未实现；不得用这些字段声称已解决 generation 隔离。清理须另冻请求完成、端点退出、旧副本排空、交换机清理、重新创建的顺序，保留全局观测账。

C2 同刻边界须分别构造 Stop／Dispose 在 Launch 前后的 event uid 顺序。零等待同步放行；放行后 Stop／Dispose 不增加取消数，当前 Stop 不停止已创建 QP。新窄测试入口或真实驱动链仍待实现，旧无驱动取消夹具不覆盖这些情形。
