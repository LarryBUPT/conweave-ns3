H12 与 E 的完整路径、时间和 FCT 相同。E 的历史技术 FCT 哈希为 `70c970c63da906181ac8745f290528c4006ac9818645eafc40af150b140b1086`；严格 Q12 为 `1f71d7e802ec1b334aff9c6708be5abc2420c6fa7c31e2b6e2f3fdb1232bb44e`，均与冻结回归契约一致。Q12 的 840 次首次选择中，301 次候选端口不同，其中 114 次队列不等；逐条符合“第二候选严格更短才选择第二，否则选择第一”。

## 3. 持久 QP、轮次原点和清理

六个持久格各创建/删除一个发送 QP，三个请求共享一个 serial，接收 QP 地址始终相同。三轮首发序号为 0、8,192、16,384；累计 `snd_nxt`、`snd_una` 和 `highest_ack` 依次到达 8,192、16,384、24,576。最终累计确认时才调用完成删除。后两轮放行前，前轮已完成；实际 RELEASE 和 FIRST_SEND 相对各轮需求均为 0 ns 等待。

`ReleaseWs30Round` 只提高已放行上限并触发发送，见 [rdma-hw.cc](../../src/point-to-point/model/rdma-hw.cc:307)。发送字节上限来自 [rdma-queue-pair.cc](../../src/point-to-point/model/rdma-queue-pair.cc:107)。原始日志中的 RELEASE 与路由序号范围也符合该上限。ROUND_DONE 的 `released_ns` 是计算字段，本分析改用独立 RELEASE 事件核对真实放行时间。

CC 的动态覆盖仍有边界。全部 16 格中，轮完成时 rate 都是 400 Gbps、alpha 为 1、SACK buffer 为 0。六个持久格没有 CNP、SACK 反馈、恢复重传或超时；跨轮 `rate/alpha` 与上一轮完成值一致，源码也未重建 CC 对象。这些证据尚未覆盖非初始 rate/alpha、非空 SACK 或恢复计时器的跨轮连续性。后续若要主张这类状态也已动态验收，须冻结专门的补验条件和新 ID。

| 条件与方法 | 三轮请求完成时间（μs） | 背景 P99（μs） | 入口首包端口 |
| --- | --- | ---: | --- |
| 背景共存，持久 E/Q12/U12 | 16.964 / 9.976 / 16.963 | 24.893 | 2 / 2 / 2 |
| 背景共存，新 QP E/Q12/U12 | 16.964 / 9.976 / 9.976 | 24.859 | 2 / 2 / 3 |
| 空队列预热，持久 E/Q12/U12 | 9.976 / 9.976 / 9.976 | 23.174 | 2 / 2 / 2 |
| 空队列预热，新 QP E/Q12 | 9.976 / 9.976 / 9.976 | 23.174 | 2 / 2 / 3 |
| 空队列预热，新 QP U12 | 9.976 / 9.976 / 9.160 | 23.174 | 2 / 2 / 3 |

表内每轮从自己的需求原点计时。持久 raw 的最终 QP FCT 包含两段空闲等待，不能代替三个请求的完成时间。背景只有 3 条流，P99 是线性插值描述量；完整三条结果保存在 JSON，不作尾部总体推断。

持久 Q12 在访问过的交换机上呈现 miss 序列 `[1,0,0]`；U12 的入口也如此。每轮新 QP 使用三个 serial、三个新端口元组，首次到达均为 miss。相同 tuple 销毁再创建时，保留缓存臂依旧为 `[1,0,0]`；显式结束清理臂为 `[1,1,1]`。Q12 清理格中交换机 4、5、7 各删除表项 3 次，交换机 6 每次删除 0 项。最终探针状态清除，其他背景状态保留。

持久与 tuple 复用探针在相关交换机上的两个候选端口全部重合。因此两轮命中直接证明缓存复用，清理的 miss 变化证明删除生效，但这些格没有形成“两个不同候选之间重新选择”的判别条件。清理与不清理的性能相同也符合该结构。新 QP 第三轮有不同候选；空队列预热的新 QP U12 虽缩短 0.816 μs，同时产生 1 次 gap、1 次 SACK/CNP 反馈、7 包共 6,192 B 重传、10 次交换机端口变化。这是单轮性能与恢复代价的同时变化，不能解释为持久 QP 优势。非平凡 CC/SACK 和持久不同候选的覆盖缺口继续保留为未完成的科学验收问题，不能用 16/16 标签替代。

## 4. seed 字段核清

[seed 审计](evidence/ws30-v13-seed-audit-r1.json)列出全部 214 格。`prepare_ws30_v13.py` 的 [cell 返回值](../../scripts/prepare_ws30_v13.py:54)把 `seed` 固定写成 0，正式循环也未覆盖该字段。这是未明确语义的默认元数据；现有文件没有把它正式声明为哨兵。

实际执行链路没有读取该值设置模拟器。[Backend.start](../../scripts/run_ws30_v13.py:162)不传 seed；[run.py](../../run.py:116)写 `RANDOM_SEED 1`；[scratch](../../scratch/network-load-balance.cc:1439)用读取值执行 `srand` 和 `SeedManager::SetSeed`；[worker metadata](../../scripts/remote_worker.py:471)记录 1。46 份实际 config 和 metadata 均核对为 1。构建收据的 seed 0 只是继承计划字段，不能当成模拟器实际 seed。

原 r2 计划字节和哈希保持原样。正式解锁前应另建修订版，明确 `simulation_seed=1`，并从 trace 文件名提取 `demand_seed`：主体为 20,263,021～20,263,044，历史为另外两组 24 个需求。实验 ID 中的 `s20263021` 表示需求生成 seed；它与共同 ns-3 seed 1 属于不同随机过程。已有 46 格不需要为此元数据问题重跑。新计划还必须明确继承这些固定 trace 哈希及旧 E/Q12 回归契约。

## 5. 资源、吞吐和 168 格预算

每格独立源码 `-j2`，最多四份并行构建。cap 8 的八份构建分两组完成，全部构建结束后才启动仿真。吞吐从 metadata 时间戳计算，不把监督等待或每个进程 RSS 当整机总量。

| 项目 | cap 4，4 格 | cap 8，8 格 |
| --- | ---: | ---: |
| 仿真批跨度 | 340 s | 383 s |
| 仅仿真吞吐 | 42.35 格/小时 | 75.20 格/小时 |
| 单格运行中位数 | 321.5 s | 356.5 s |
| 单格构建中位数 | 416 s | 412 s |
| 首次创建至最后完成跨度 | 765 s | 1,223 s |
| 构建加运行吞吐 | 18.82 格/小时 | 23.55 格/小时 |
| 峰值 load1 | 6.82 | 8.09 |
| 最低可用内存 | 104.87 GiB | 87.23 GiB |
| 最低空闲磁盘 | 2,997.76 GiB | 2,984.11 GiB |
| 单实验进程树 RSS 峰值 | 4,545.25 MiB | 4,545.13 MiB |

cap 8 的仿真吞吐较 cap 4 增加约 77.5%，构建加运行吞吐增加约 25.1%；单格运行中位数增加约 10.9%。E/Q12/U12/DRILL 在两档及 cap 8 重复间的 FCT 哈希分别相同。只有一个独立需求和一次资源阶梯，无法把差异作为跨日容量保证。

资源 pilot 的双侧结果为：E/Q12/U12/DRILL 的消息批时间分别为 18.088/16.944/21.656/15.026 μs，背景 P99 为 2,129.418/2,116.389/2,141.020/2,239.150 μs。U12 的两侧变慢和 DRILL 的背景尾部增加均保留。这里的重复仅用于调度确定性；同一需求的三份输出不能算三个独立需求。

若主对话随后解锁 168 格，建议采用已测 cap 8，继续 `-j2`、最多四份并行构建，以及现有 load1≤20、可用内存≥32 GiB、磁盘≥100 GiB、单实验树 RSS≤32 GiB 门槛。维持构建与仿真分阶段的调度即可复用当前实测。cap 12 尚无本源码新鲜 pilot，当前不据旧数据批准。

按已测吞吐，168 格仅仿真约 2.23 小时，计入逐格隔离构建约 7.13 小时。cap 4 的相应值约 3.97/8.93 小时。再预留回传、核验和分析 1.5～2 小时，以及失败恢复缓冲。cap 8 最后八份源码及结果约新增 13.65 GiB，线性估算 168 格约 287 GiB；这是存储预算，启动前仍须核新鲜资源和未知作业。R12 未进入大输入资源 pilot，正式首批也须检查其耗时。新 W5 的 36 格建议单独列预算，见[设计审计](ws30-w5-baseline-comparability-and-pilot-r1.md)。

## 6. 参考借鉴复核与剩余门槛

本节点从项目根目录候选 README 和 reading-log 进入，核对 ConWeave、Gemma、SeqBalance、DiffFlow、SGLB 和 Flowcut 的技术分析、核验记录及固定 PDF。[参考与基线审计](evidence/ws30-v13-reference-and-baseline-audit-r1.json)保存文件哈希、版本、作者代码检索范围和原生源码 blob 对照。

SeqBalance v1 提醒本节点区分连接、子请求和父级完整完成；本夹具没有 WQE 拆分或父 CQE 聚合。Flowcut v2 提醒清理前须有可观测排空条件；本夹具以最终累计 ACK 后显式删测试 tuple，未实现它的 ACK 清账/窗口切换。ConWeave 与 Gemma 的阶段重排使“QP 尚活跃时仍有数据可触发决定”成为 W5 的设计重点；两篇论文收益不代替当前输入实测。DiffFlow 的在线分类与规则安装、SGLB 的全局状态传播均应核算成本，不能只借名称增加基线。具体可比性和不能外推的条件列在 W5 文档中。

本节点已完成全部 46 格运行与原始证据分析。严格无标签入口、回归、不干扰观测、持久对象/累计 ACK 和缓存命中清理获得有界支持。非初始 CC/SACK 连续性、持久不同候选的动态判别，以及 W5 新负载和外部算法忠实度仍待主对话确定承接。正式解锁还需要修订 seed schema、主对话验收及新鲜资源门槛。本节点未修改论文、审稿回复或原生算法，也未接触 WS-29。
