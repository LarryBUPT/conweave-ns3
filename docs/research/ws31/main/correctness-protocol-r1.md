## 2. 先做预检，再进入网络格

先在新固定 SHA 下完成完整 optimized `-j2` 构建、Ofan 可移植核心测试，以及 `scratch/ws31-start-lifecycle-test` 的 Stop/Dispose 两项测试。后者没有网络、驱动或数据传输，仅验证等待事件取消；不可把它计入吞吐或网络仿真结果。

每项使用独立目录、日志和来源收据。旧固定源码 `bc4de1e…` 的完整构建不能替代增加 Ofan、输入和取消夹具后的新构建。已有 C1／C2／C3 核心测试不重复填充运行数。

## 3. 网络正确性格与通过条件

先执行 QueuePin 和三个零控制的四格 pilot：`ws30v13-q12`、`ws31-c1-zero`、`ws31-c2-zero`、`ws31-c3-zero`。全部输入完成，FCT 八列逐字节相同，时间起点与公共输入转换一致，才进入其他技术格。

主输入后续覆盖 C1 的类别、统一、活动计数、历史、大小和统一计数；C2 的类别、统一和大小；C3 的类别、固定和大小。主输入只有固定两尺寸，C1／C2／C3 各自主模式应分别与大小控制保持完整输出等价。这个预期来自当前标签—大小绑定，不能当成业务语义超出大小的证据。

未知输入覆盖 QueuePin、C1 类别／统一、C2 类别、C3 类别。C2／C3 未知标签应与 QueuePin 保持相同输出；C1 未知应与统一模板控制相同。标签清零／互换的干预格另记录输入变换和哈希，不改变其他配置。

动态门：C1 至少观察到非零预测压力及后续扣减；C2 有非零等待且原需求、放行、完成满足顺序，FCT 包含等待；C3 新准入限制、首次借用、重新激活与旧借用者持续发包均被覆盖。若未触发，记为覆盖不足，可设计新的明示技术夹具，但不能把该格当作候选效果筛选或依据收益改参数。

Ofan 和匹配的 `ofan-rr` 控制分别运行脊叶及小型三层输入。RR 控制与 Ofan 共享包长分组、初始化和每包推进，仅将指针按 next-hop 集合合并，不按目的必经节点合并。旧 `packet-rr` 只作用于 tag 2，且按目的主机维护指针，不用于这一匹配比较。两种模式都必须记录数据及 ACK/NACK 实际轮转、分组独立性和下行负载；三层输入必须出现非零 aggregation 分组。普通 RR 的下行表现不要求一定更差，但必须证明两种调度规则真实不同。

## 4. 身份、计时、资源与停止线

`scripts/verify_ws31_fct.py` 检查全部请求的 tuple、字节、需求起点和完成，而非只检查统计窗口内已完成流。公共框架在 WS-18 之外保留旧 seconds-double 到纳秒的截断；C2 使用相同需求事件，不将等待后的时刻当作起点。验证器按实际二进制浮点转换检查这一口径，必要时与 QueuePin raw 对照，不能静默平移 1 ns 或重写输入。

每格保留固定 SHA、拓扑和输入哈希、配置、实验 ID、raw 和资源收据；任何构建、守恒、计时、回退、回归或分组失败都停止后续格，修复后用新 SHA／ID 验证，保留失败。独立格不得共享可变输出。先用单格资源 pilot，不能为缩短运行而绕过锁或重启旧控制器。

这些技术格全部通过后，仍待独立需求下的双侧效果、开销与最终贡献判断。性能协议需要另行冻结；本协议不继承任何旧矩阵，不以技术样本的改善选择正式场景或阈值。
