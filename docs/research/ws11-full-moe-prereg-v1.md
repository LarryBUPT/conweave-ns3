# WS-11 全量同步 MoE 加背景现象：预注册 v1

冻结：2026-09-26（中国时间），在任何 WS-11 全量仿真前。本文件以个人 fork 的提交 SHA、`scripts/audit_ws11_inputs.py` 输出、四份版本化输入和拓扑为契约。WS-10 的 256 目标、固定总字节、五 seed、主 4 档 no-go 是独立实验，不能被本实验重新判定或补样本。WS-11 只有在本文件的现象门槛通过后，才允许开启效果对照。

## 1. 已知输入、问题和边界

四份 `config/moe_1280group_256to8_8round_8KB*.txt` 的 SHA-256、行数、tag、流大小、同步起点和热点静态画像以 `docs/research/ws11-input-audit.json` 为准；拓扑 `topo_1280_400G_400G_OS1.txt` SHA-256 为 `74a6f7154ca10c3cd6dfd45046c4f8abf0ce27faa8ad11446b6a52920b83afba`。四档 MoE 均是相同且同序的 16,384 条 8 KiB、`tag=2` 流，在 2.000000000 s 同启；背景 `tag=1` 为 0/64/128/192 条 8 MiB，后档嵌套前档。MoE 提供 128 MiB；四档总提供 128/640/1152/1664 MiB。静态热点：256 个 MoE 源、256 个目的，单源最多 64 流，单目的最多 84 流；四 rail 拓扑仅 rail 0 承载这些输入。文件名的 `8round` 不是 trace 中的轮次字段。

问题：在这个**固定 MoE 集合、逐档增加背景字节**的场景，同一共同接收条件下，`dualtrack` 相对全流 `fecmp` 的 MoE 尾部是否随背景增加而稳定恶化，同时背景流本身不承担不可接受的代价？这只能识别算法 × 增加背景负载的交互，不能单独识别“混合比例”的纯效应。原始 MixHash `lb_mode=16` 的所有 UDP 数据均走带计数器的 ECMP，且它有独有重排/传输代码；导入的 trace 不等于导入其机制。WS-11 主现象对照仍为本 fork `fecmp` 与 `dualtrack`，两者复用同一份字节级 trace。

## 2. 运行契约与重复

固定拓扑、400 Gbps、9 MiB buffer、DCQCN、PFC=0、IRN=1、`simul_time=0.01`、`netload=10`、同一 Waf optimized 源码 SHA 与分析脚本版本。主输入是上述四份原始文件；不从流量生成器随机生成 trace。`RANDOM_SEED=1` 固定，避免把传输随机性误称独立需求样本。每格的源码 SHA、原始 trace SHA、拓扑 SHA、配置、seed、原始 FCT/CNP/PFC/uplink、日志、资源收据和算法计数必须保留；各档算法配对只变 `LB_MODE`。

先运行一组原始文件的 4 档 × 2 模式，作为**原始输入完整复现**。为了检验同步事件与端口分配的敏感性，另以预定 PRNG seed `20261101`–`20261104` 对每档**相同完整流记录多重集**作确定性行顺序置换：同一 seed 内 MoE 顺序跨四档相同，背景顺序嵌套；固定行记录、起点、类别、字节和端点不变。每个置换的四档 × 两模式共 32 格。总共五组、40 个现象格；原始组标为 `original`，四组标为 `order-permutation`。这些重复改变端口分配及同一时刻的事件顺序，**不是五个独立需求抽样**；组是分析单位，不用 16,384 条流作独立样本或报告需求总体置信区间。若置换生成脚本无法严格核验流记录多重集与档位嵌套，不启动正式格。运行顺序每组交错模式，预定为 `0:fecmp, 0:dualtrack, 64:dualtrack, 64:fecmp, 128:fecmp, 128:dualtrack, 192:dualtrack, 192:fecmp`；组按 original、20261101–04 顺序。

## 3. 预定指标、判据与归因控制

`scripts/analyze_moe_tags.py` 以输入 trace 为分母逐流匹配原始 FCT。主 MoE 指标为所有 16,384 条完成时的**合成批次完成时间**，即最晚完成绝对时间减 2.000 s；另报告 MoE 完成率、FCT P50/P95/P99、完整源批次 P99。按静态输入频次最高的前 8 个目的（以原始 MoE 文件排序，遇并列按目的 ID 升序）报告各自流数、完成率、FCT P99 和最晚完成时刻；热点口径在效果数据前固定，不能结果后挑热点。背景侧报告全部背景流完成率、P50/P95/P99 与最大 FCT。每格另列原始 CNP、PFC、uplink 按 ToR/端口窗口利用率和不均衡；NACK/超时若未有可靠原始计数器，标记不可得，不用日志文本缺失推断为 0。空的物理 queue 文件不等于 0 占用，ConWeave VOQ 也不是 MMU 队列。

对组 `s`、档 `b`，定义 `I_s,b=(P_s,b−P_s,0)−(F_s,b−F_s,0)`、`R_s,b=I_s,b/P_s,0`；`P/F` 为 dualtrack/fecmp 的 MoE 批次时间。**唯一主档是 192**。现象 go 当且仅当五组 40 格均源码/输入/拓扑核验通过、两类输入 100% 完成，至少 4/5 组的 `I_s,192>0`，五个 `R_s,192` 中位数 ≥5%，且每组 64/128/192 背景 P99 相对同组同档 `fecmp` 均不恶化超过 5%。64/128 档是预定剂量与非单调性检查；逐组报告其正负和幅度，不得事后取代 192 主档。背景 P99 每档有 64–192 个流，仍以组而非流为重复单位。若任一门槛失败，即 no-go，完成的负结果保留，效果比较不启动。若资源停机使 40 格不完整，只报告已完成数据和未判定，绝不称 go。

每档 `fecmp` 与 `dualtrack` 均使用完全相同的增加负载，故上述双重差分扣除了共同的总字节增加效应；它并不能排除算法本身对负载的非线性响应。报告每档提供字节和 `fecmp` 自身增量，并以 WS-10 的固定总字节 no-go 作为**不同场景的边界证据**，不合并效应。若本轮通过，效果阶段还须在同输入、同组、同资源约束下设置可核查的等信息对照，不以不同总字节档之间的直接差值宣称类别信息收益。

## 4. 条件性效果阶段（本门槛前关闭）

现象 go 后另冻结效果矩阵及预算，才比较 `shortq2`（普通双候选）、`guardhash`（类别评分）、`guardhashgate`（HarmGate 开/关）、始终共享与静态隔离，并实现或核查 APS/FLB-like 强对照的**相同可用信息、更新频率、队列观测与哈希候选**。每组同 trace/传输/seed 配对，先证明每算法所有流完成及计数守恒，再看相对 `shortq2` 的 MoE 批次/热点尾部增量、背景 P99 与坏处、门控激活和状态成本。无法达到信息等价的强对照须明确降级为机制参考，不可作为优势结论。若类别信号增量不稳定、背景损害 >5% 或状态/标签成本不可接受，保留负结果，不升级 GuardHash 主张。原始 MixHash 仅作为来源机制参考；未移植其额外重排时不声称算法级等价。

## 5. 资源 pilot、并发与停机

先审计服务器其他用户、运行器单仿真拦截、启动竞态、共享 Git 缓存、Waf 构建目录、`mix/output`、`mix/.history`、输出与结果 ID。原始 192 背景 `fecmp` 单格作为资源 pilot；仅在其全类可解析与资源达标后可追加原始 192 `dualtrack` pilot。pilot 与正式数据分开，不因 pilot FCT 的方向改主档或门槛。每格记录 build/simulation 墙钟、仿真进程峰值 RSS、可用内存最低值、工作区空闲盘最低值、目录增量和 SHA。启动新格要求 1 分钟负载 ≤20、可用内存 ≥32 GiB、空闲盘 ≥100 GiB、无未知 ns-3 进程或其他用户重负载。单格编译 >30 分钟、仿真 >4 小时、RSS >32 GiB、单格磁盘新增 >10 GiB、WS-11 累计新增 >400 GiB 或累计仿真 CPU 预算 >160 core-hour 时停**新格**并保留证据；运行中资源跌破线或出现其他用户任务则暂停新启动并降级并发。超时/未完成、输入 SHA 不一致、原始数据不可解析、PFC 非空或计数不守恒也停止扩展并保留失败 ID。

当前运行器默认一次一格；只有审计、锁与独立状态/目录改造经过并发试验，且实测 pilot 的 CPU/RSS/磁盘证明余量，才允许逐级 `1→2→4`，绝不通过跳过现有拦截多开。每次提升先观察至少两格的完成率、吞吐与资源峰值；自动降级条件为负载 >20、可用内存 <32 GiB、空闲盘 <100 GiB、出现未知 ns-3/其他用户活动、失败率非 0 或吞吐不增。仿真后台静默，控制器将收据写入忽略的 `results/`，低频汇总；中断后只从已核验收据恢复，不覆盖实验 ID、原始结果或收据。若 pilot 显示 40 格不可承受，停在 pilot 阶段，另立版本化设计而不把缩样本结果按本门槛解释。
