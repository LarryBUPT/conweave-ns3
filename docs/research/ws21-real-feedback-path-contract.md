# WS-21 真实反馈报文工程契约与首版实现

更新：2026-09-29。范围仅是把下游候选信息做成经过仿真网络的显式报文，并核验送达、成本和失效退回。它不是效果实验协议；WS-21 效果矩阵保持关闭。

## 为什么采用显式报文

WS-21 长尾诊断 pair 已证明目的 ToR 能把所选上游路径的 CE 包归属到 16,205 个跨 ToR QP，但信息没有返回源 ToR。代码审查确认 `SwitchNode::SwitchSend` 会将交换机产生的数据包放入 `QbbNetDevice` 的实际出口队列；途经交换机由 `SwitchReceiveFromDevice` 和现有路由表转发。ConWeave 的 `SendNotify` 已提供在交换机生成 IPv4 控制包并经交换机发送的代码范例。新通路沿用真实 Qbb 链路、传播时延、队列及丢包模型；禁止用 PacketTag、跨节点直接读状态或零延迟回调代替反馈。

## 报告内容与归属

目的 ToR 以 `(源 ToR, 目的 ToR, 源候选首口)` 为键，在目的 ToR 入端按 `WS21` 已核验的 `(源 ToR, 入端口) → 源候选首口` 映射归属数据。报告使用固定宽度、可序列化的 IPv4 控制协议头，至少携带：版本、源/目的 ToR ID、候选首口、观察窗起止仿真时间、CE 包数、样本包数、单调序号和生成时间。分子、分母不可省略；分母为零时表示“无样本”，不能编码成零拥塞。报文使用原始目的主机 IP 作为返回源地址、原始源主机 IP 作为目的地址，借助现有交换机路由表回到源 ToR。协议号须在实现时确认当前没有被其他分支占用，并在所有解析、长度计算、序列化及反序列化路径一致注册。

源 ToR 只接受匹配本机、源/目的 ToR 与候选端口合法的报告；以 `(目的 ToR, 候选首口)` 缓存最高序号。旧序号、未来采样时间、非法候选和重复报告均拒收并计数。缓存记录样本数、拥塞等级、采样时间、到达时间、序号及有效/无效原因。建议的 10 µs 报告周期与 10 µs 新鲜度仅是首轮工程参数；必须在长尾 pair 实测送达年龄后再冻结，不能由旧效果结果调参。源端实际决策时刻必须晚于报告到达；过期、缺失、乱序或无样本一律回退到现有本地双候选队列决策。

## 网络路径、队列与计费

1. 目的 ToR 在每个非空观察窗生成一条报告；只对活跃候选键发送，定义并核验无新包后的停发/撤销规则。报告不得逐数据包产生。报告窗口与序号只使用仿真时间，不依赖墙钟。
2. 目的 ToR 构造带普通 IPv4 头和专用序列化反馈头的完整 packet，经标准目的地址路由和 `SwitchSend` 进入真实出口设备队列。不能调用 `DoSwitchSend` 伪造已排队状态，也不能把报告放入 ACK/NACK/PFC 的最高优先级队列；新协议须有明确的数据队列映射。普通交换机按 IPv4 目的地址转发，不解析或改写反馈内容。
3. 源 ToR 在 `SwitchReceiveFromDevice` 的最前端识别并消费反馈协议包，更新本地有界缓存，不把它交给主机 RNIC。控制包回程必须经过与其他数据相同的链路时延、设备队列、ECN/丢包和传播过程。
4. 对每条报告记录生成数、端到端送达数、丢失/过期/拒收数、线上模拟字节数、逐跳排队/出队时间、生成至送达年龄、端到端 hop 数、序号缺口、最大活跃键与源端缓存规模。线上字节数从实际 packet 长度及每跳成功/丢弃事件计算，分开报告逻辑负载与链路帧开销。诊断日志有界，计数器守恒；任何日志/事件溢出使该门槛失败。

## 路由决策边界

模式 20 的现有本地臂继续作为缺失或失效回退。实现首轮时保留旧两候选哈希与本地队列读数；真实反馈只进入明确标记的 WS-21 实验开关。报告的 CE 比例仅描述包已走过的上游路径；目的 ToR 最终唯一主机出口产生的拥塞不得被伪装为候选差异。需要先用现有 ingress→first-hop 映射验证上游候选归属和 CE 观察窗，再决定量化等级。候选间样本不足时显式记“不可区分”，回退本地臂。

实现需将诊断事件分成 `generated`、`hop_enqueue`、`hop_dequeue`、`drop`、`delivered`、`rejected`、`adopted`、`expired`。接收日志只证明送达，不证明采用；采用日志需关联源 ToR 决策时间、报告序号、采样时间和 age。若报告在下一条 QP 首次选路后才到，必须记录为迟到且不得追溯改变已锁定路径。

## 本地实现检查与停止条件

- 协议头需有固定长度和独立序列化/解析测试；短包、未知版本、无效样本数、错误 ToR/端口和序号回绕须被安全拒绝。
- 先静态检查无反馈开关时旧 mode 20 与原始 WS18/WS21 文件行为不变；控制报文不改变任何应用流的输入、选口或完成计量。
- 反馈启用时，空载由目的 ToR 到源 ToR 的探针必须经过真实拓扑；核对每跳队列与时延，并验证在拓扑丢包或故意延迟时触发丢失/过期回退。
- 在冻结远程 SHA 前完成代码审查、编译和最小正确性测试；再用新的固定 40 流输入做同 SHA 开/关非扰动 pair。只有此门槛通过，才用未重命名的 WS-17 长尾输入做新的真实反馈技术 pair，测长尾送达、状态上限和资源成本。WS-19 旧 ID 不可替代新 pair。
- 任一映射冲突、报告归属歧义、无路由、状态/日志溢出、回退不严格或控制流量无法计费，停止该实现并保留本地路径臂；不得启动效果矩阵。

## 当前证据等级

契约源自 `switch-node.cc`、`qbb-net-device.cc`、`conweave-routing.cc` 和 WS-21 当前诊断收据。首版代码加入了独立 51 B 反馈头（IPv4 协议 `0xFA`）、目的 ToR 10 µs 非空窗聚合、普通 Qbb 队列返回、源 ToR 校验/缓存/过期拒收、基础汇总计数和默认关闭的 `run.py --ws21-feedback` 开关。固定提交 `3f1a28a6583567744b6a177d8c11da7cc8a761dc` 在隔离构建 `20260929-153553-ws21-feedback-wire` 的 optimized `-j2` 编译成功；远端 `devices-point-to-point` 套件通过，包含反馈头字段序列化/反序列化检查。全量测试构建需临时修正一处无关 core 测试的 const 声明，构建后已恢复原文。

当前接收缓存尚未改变选路，也没有按消息输出完整逐跳时间线；10 µs 周期/有效时限尚未校准。仍无新的仿真实验 ID、真实送达率、反馈年龄/线上成本或采用数据。该结果只关闭构建和报文头单测门槛，不代表完整通路已验证；完整技术 pilot 未就绪，效果矩阵与历史 no-go 均不变。
