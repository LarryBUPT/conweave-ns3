# WS-30 formal-rest 控制器修复与续跑准备

日期：2026 年 10 月 26 日。实际修复与审计模型为 GPT-6.1 Sol / Medium，已由当前会话的 `turn_context` 核实。本节点完成控制链路修复和本地验收，140 格续跑等待主对话验收。新增构建、仿真均为 0。

## 1. 实验断点与故障根因

formal-first 的 4 格已验收。formal-rest 共 164 格，其中 24 格的原始结果已保全，剩余 140 格未启动。正式矩阵合计已保全 28/168 格。全部正式格仍使用固定仿真源码 `2c9f3a50bafad0740b461496ba24fa81941a9bc7`、模拟 seed 1 和冻结输入。

2026 年 10 月 26 日 09:23:44 UTC，原控制器以退出码 1 停止。`run_ws25_preflight.command()` 使用系统默认编码读取子进程输出。Windows 的输出读取线程发生 `UnicodeDecodeError` 后，`result.stdout` 为 `None`。错误处理继续对它执行 `[-1600:]`，又抛出 `TypeError`，掩盖了原始子命令的退出细节。原收据因此留下 `validation` 失败，而不是逐格仿真失败的证据。

原执行收据保留 18 条 verified 和 8 个 pending ID。中断时这批 8 格的远端状态均为 `SUCCEEDED`；随后补齐结果与日志，24 格全部通过独立 raw 核验。旧收据、恢复收据和已有实验目录均保持原值，续跑计划按 SHA-256 封存这些证据。原子命令的具体非零退出原因已经丢失，本次修复不能恢复该段输出。

另一个恢复缺口是 `config.log` 的收集顺序。完整结果下载已经包含 `raw/<数字ID>/config.log`，旧 helper 仍额外通过 SCP 下载日志副本；若此时中断，已有本地目录会直接进入验证，缺失的 `logs/config.log` 没有恢复机会。旧 SCP 还直接写最终文件，部分下载可能被后续的“文件已存在”判断跳过。

## 2. 已实施的修复

| 修改 | 作用 |
| --- | --- |
| `run_ws25_preflight.command()` 使用二进制管道，子 Python 明确使用 UTF-8 | 避免输出线程按 Windows 默认编码解码；显示诊断时才容错解码 |
| 失败和超时保存完整输出字节及 JSON 收据 | 保留退出码、命令参数、输出哈希和超时部分输出；`stdout=None` 也能报告原退出码 |
| 本地 SSH 输出路径明确采用 UTF-8 和容错诊断解码 | 覆盖 stage3、v13、v14、资源检查、trace 检查及流式 build 输出；仿真 raw 字节不参与替换解码 |
| `fetch_config_log()` 优先读取已下载的 raw 日志 | 在本地恢复日志副本，并逐字节哈希核对；已有不同副本立即拒收并保留 |
| 远端补抓先写唯一临时文件，再校验哈希并发布 | 中断留下临时证据；最终日志路径不会接纳部分下载或覆盖既有文件 |
| v14 的本地目录验收先补齐日志副本 | 结果已下载但日志副本尚未生成时，可继续收集；最终验收要求副本与 raw 日志哈希一致 |

固定仿真源码、trace、拓扑、worker 和实验参数没有修改。远端没有部署或同步新的 worker。

## 3. 续跑边界与碰撞保护

新入口为 `scripts/resume_ws30_v14.py`。默认 `inspect` 只读本地。`prepare` 核验当前 Sol / Medium 会话、已有 raw 和远端目录；它不构建、启动、抓取、同步或部署。`run` 要求独立的主对话验收收据和实际 Luna / Medium 会话。

[续跑计划 r2](evidence/ws30-v14-formal-rest-resume-plan-r2.json)冻结了以下范围：

- 已保全 24 个 ID 只做重新核验；其 FCT、metadata 和日志哈希均与原恢复收据一致。
- 140 个 ID 按原阶段顺序逐项列出，每格仍绑定原源码、输入、需求 seed、模拟 seed 和 cap 8 上限。
- 同时检查远端 `runs` 和 `results` 路径，拒绝只有目录而没有 metadata 的残留。
- 检查本地正式结果、`.incoming-<ID>-*` 和 build intent；已有痕迹须先解释，不能当作空 ID。
- 使用独立状态文件 `results/ws30-v14-formal-rest-resume-execution-r2.json`；旧失败状态文件不再写入。
- 再次恢复时，只接受本续跑状态中已保留的 batch reservation 和匹配的 build intent。远端已成功格走抓取与核验，已有本地结果走日志恢复与核验；两条路径均不重建或重跑。
- 构建返回不明、目录来源不明、源码或输入不符、部分下载、raw 验证失败和资源异常都会停止新 admission，并保留证据。

现有阶段授权仍是原 164 格 formal-rest。新计划没有扩大授权。[新的续跑审批收据 r2](evidence/ws30-v14-formal-rest-resume-authorization-r2.json)为 `approved: false`，`main_chat_acceptance` 为空。它已经列出新控制哈希和计划哈希，供主对话核验后填入实际验收依据。旧授权文件未修改；旧入口会因控制哈希变化而拒绝继续运行。r1 计划、审批和本地审计作为未批准的准备稿保留，r2 补入了旧编码终端的流式输出回退。

主对话放行并实际切换模型后，运行入口为：

```text
python scripts/resume_ws30_v14.py run --session-file <本会话实际 Luna Medium 的 JSONL 文件>
```

入口会再次核验封存证据、保全格、目录、worker、控制哈希和新鲜资源。准备时的资源快照不能替代启动检查。原固定源码的 cap 8 资格继续适用；工程新源不继承这一资格。
