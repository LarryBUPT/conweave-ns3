# WS-21 反馈设计复审：技术 pilot 尚未就绪

日期：2026-09-28。范围：本地源码、固定拓扑、WS-19 六个 ECMP/192 旧实验 ID 的 trace/三时刻 raw，以及 WS-21 首版[可行性记录](ws21-downstream-feedback-feasibility.md)。本次只产生静态预算和设计纠错，**没有修改仿真算法、没有远程编译或新实验 ID**。复算脚本为 [`audit_ws21_static_budget.py`](../../scripts/audit_ws21_static_budget.py)，逐格输入、固定仿真 SHA `b52e66f0fbf786fb57672b12a5633cf45b9311c1`、拓扑/trace SHA 与 `SUCCEEDED` 元数据经脚本断言；可用 `python scripts/audit_ws21_static_budget.py --verify` 重验[机器记录](evidence/ws21-static-budget.json)。该记录的消息数是明确假设下的**预算**，不是实测控制流量。

## 复审发现

| 问题 | 旧 raw 和源码给出的边界 | 对首版设计的修订 |
| --- | --- | --- |
| 时间桶过短 | 六格各有 16,576 条全完成流。背景单流最长 `finish−demand` 为 2.325–13.287 ms，完整观察窗同量级；此前提议的 64×1 µs 只覆盖 0.064 ms。 | 撤回“0.38 MiB 可覆盖背景尾部”的估算。以共享**目的出口端口**而非每 QP 采 1 µs 队列高水位，QP 自身仅留反馈/速率/重传转折事件；按旧格 108–115 个背景目的主机出口和完整观察窗估算，密集记录需约 8.5–47.2 MB 逻辑数据，文本和运行时开销还未计。必须保证长达 13.3 ms 的尾流不被环形缓冲覆盖，或把溢出明确判为观测失败。 |
| 反馈 key 的下游身份尚未**实现和动态验证** | 16,384 条 MoE 中约 15,960–16,020 条跨 ToR，每格产生 1,549–1,559 个源/目的 ToR pair。两候选是**每条流**分别哈希，同一 pair 的流合计可用八个上联；因此活跃 `(源 ToR,目的 ToR,候选首口)` key 静态下界 3,098–3,118、上界 11,848–12,138，实际值尚未重放哈希。`DoLbWs18` 只在源 ToR 的 `m_ws18FlowPort` 存本地出端口。拓扑最短路审计发现六格所有 pair 的“源首跳候选→目的 ToR 入邻居”集合**互不重叠**，所以本拓扑存在从 `(源 ToR,目的 ToR,目的入端口)` 反推首跳的静态映射；但模式 20 尚未建立或逐包校验。 | 优先实现并校验拓扑映射表，而非先假定必须新增数据包路径 ID。技术 pilot 要记录源实际首口、目的实入端口及反推首口的逐 QP 一致性；遇到非最短路、拓扑变化或冲突时标为无效并退回本地臂。反馈消息仍需真实线上编码和成本。共享目的主机出口仍不能给候选提供差异化分数。 |
| 周期报告预算未封顶 | 若对所有 key 从最早 demand 到最晚 finish 每 10 µs 报一次，六格按上述 key 上下界为 0.726–16.131 **百万**报告、11.6–258.1 MB 的 16 B 逻辑负载；其中每格上下界须成对读，不能把范围当实测。若只在每 pair 首次 demand 到该 pair 最后完成期间报，为 91,144–381,858 报告、1.46–6.11 MB 逻辑负载。均未计包头/排队/处理，且下一轮首包可能在报告到达前决定路径。 | 不能直接冻结“每 key 10 µs 周期广播”。需定义订阅/取消、空闲停发、报告合并或事件触发、源 ToR 的 key 数上限、失效退回及没有反向业务时的显式送达。仅有逻辑负载不能判定网络成本；必须逐个控制包记录线上字节、延迟、丢失、处理量和最大状态。 |
| 40 流技术输入覆盖有限 | WS-18 的 40 流输入能验身份、三时刻与开关非扰动，但没有 WS-19 的 16,576 QP、13 ms 背景尾部和 3 千量级反馈 key。 | 40 流开/关同 SHA pair 只能作第一道正确性门槛。若要声称长尾观测无溢出和反馈预算可承受，还需另选一条**固定旧需求 trace 的新诊断开/关技术 pair**，固定新源码 SHA、新实验 ID，原 WS-19 格不能充作该 pair；该 pair 仍不是新机制效果样本。 |

首版提议的 `2-bit` 等级、`10 µs` 时效和 `16 B` 逻辑报告均只是可审查参数；不能从旧格选有利值。旧六格主机热点的 MoE 最晚完成距首需求约 0.867–0.872 ms，而背景最慢需约 12.68–13.29 ms；ToR 热点对应约 0.366–0.372 ms 与 2.32–3.65 ms。这说明若仅为 MoE 路径维持反馈，必须事前定义何时停发；若背景还要参与信号估计，必须保证较长观察窗，不可把停发后的无观测写成队列为零。

本地源码还给出一个比共享目的出口队列更贴近路径差异的**待验采样候选**：`QbbNetDevice::Receive` 解析 `CustomHeader` 后，目的 ToR 的 `SwitchReceiveFromDevice` 尚未执行本交换机的最终出口 `SwitchNotifyDequeue/ShouldSendCN`；此时 `ch.GetIpv4EcnBits()==3` 可表示包沿**已走过的上游路径**收到 CE 标记。用入端口和上述拓扑映射按 `(源 ToR,目的 ToR,源首跳)` 汇总一个有分子/分母及时间窗的 CE 比例，理论上可区分候选，且不把最终共享出口的本次标记混入采样。它是源码时序推论，不是已经运行的反馈信号：需确认实际所有相关包按该路径映射、ECN 标记来自哪些上游跳、窗口内是否有足够样本；无样本时报告缺失而非零。目的 ToR 产生报告后如何显式送达源 ToR、如何计费和过期仍完全待工程定义。

## 技术门槛与下一可执行动作

**评审结论：首版 WS-21 技术 pilot 方案目前 NO-GO；不是机制性能 no-go。**旧 raw 证明时间桶不足、报告成本定义不全；拓扑虽给出无重叠的首跳反推线索，但运行时身份校验仍缺。此时直接编译首版“非扰动探针”无法验证完整时序和候选映射，因此不启动远程格，也不冻结反馈效果矩阵。原 WS-20 确认性 no-go 与 WS-10/11/12/19 结论不变。

下一可执行的仍是**本地设计修订**：先在源码层明确稳定 QP ID 如何跨 `DoLbWs18`、中间转发、目的 ToR 和 RNIC 关联，把已静态成立的首跳↔目的入端口映射做成拓扑初始化表，并设计逐 QP 动态核验；选定可区分候选的下游采样跳点，给出真实线上报告编码及转发规则。把每端口 1 µs 时间序列改为可持续到最长目标流完成的流式写盘/有界稀疏事件方案，并估算写盘速率与上限。对最多 12,138 个候选 key 的静态上界、订阅周期和无反向流场景给出确定的停发/过期规则，再做代码审查。若动态路径不符合静态映射、找不到可区分下游跳点或反馈 key 无法无歧义归属，应停止这一候选，保留本地路径臂和 oracle 诊断边界，不为运行实验而发明零延迟共享内存。

本地修订通过后，技术 pilot 的**固定输入**先用 `config/ws18_1280_correctness.txt` SHA-256 `4e7d0e6a68e3230e8960a174e570a0a788c191fa0b44922408867b02c25782cc`，拓扑 SHA-256 `74a6f7154ca10c3cd6dfd45046c4f8abf0ce27faa8ad11446b6a52920b83afba`，DCQCN/PFC=0/IRN=1/ns-3 seed=1；第二阶段如需长尾技术覆盖，预选 `results/ws17-demand/ws17_seed20261701_tor_hotspot_b192.txt`（SHA-256 `9996372ea22158ca995937c727b6fef20559e0ce910b22e77529d9a8061b0cc3`）。诊断源码尚未实现，因此**没有可冻结的新仿真 SHA**；先完成本地实现/审查并提交、推送个人 fork，再把确切 SHA 写进运行契约。每阶段同 SHA 开/关日志两格必须逐流 FCT、WS18 三时刻哈希相同，输入/完成/字节守恒，源选口/目的出口配对、时间顺序和无溢出成立；第二阶段另核控制包数、线上字节、时延/年龄分布、缺失/乱序退回、活跃 key 峰值和 CPU/内存/日志收据。任一失败即停，不把技术格算入效果重复。长时运行仍按工作流静默和实际模型切换规则执行。

WS-22 重排预算、WS-23 拥塞流隔离和 WS-24 多 rail 仍缺各自前置证据；不能为了续接编号自动启动。WS-25 仅整合真正做过的静态、技术或效果证据，分别标注等级。
