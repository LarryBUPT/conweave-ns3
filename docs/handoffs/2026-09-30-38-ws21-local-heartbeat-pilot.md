# Handoff 38：WS-21 局部心跳技术 pilot 与代价收束

1. **本对话目标：** 来源任务“WS-21 下游反馈机制可实现性与观测设计”（Codex task `01a0e859-cb07-7c20-a001-38f271ddd0bf`）。用户要求把受 SGLB 启发的通信适配为本项目的精简报文、局部维护心跳，并比较更新间隔与额外通信开销；分析用 Sol、实验用 Luna，最后以自然语言说明。原论文所谓 Open、Keepalive、Area Descriptor、Request、Update 是 SyncMesh 五类控制消息，不是五种心跳状态。本阶段仅收束已冻结的 HELLO/ACK 小拓扑技术试验。

2. **已确认的项目事实：** 仿真固定个人 fork 源码 `770b6b5617657832393bd721e0d634c6639405fb`、seed 1、52 节点拓扑及一条 67,108,864 B 跨 ToR 流。固定 Git 拓扑内容和六格远端快照 SHA-256 为 `dcca23ca6992b9b81e5b71127a3698264441390455f3dd29b459e33db29915ad`；预飞行曾写的 `445cf1e2…` 是同内容 Windows CRLF 工作副本哈希。trace SHA-256 为 `032b6baaf3b1a6b4507a7699ef3a148eeadd1f343a13c61a12b79c65f1d49ff5`。各格元数据、快照和 raw 均由[机器摘要](../research/evidence/ws21-local-heartbeat-pilot.json)与[分析器](../../scripts/analyze_ws21_heartbeat_pilot.py)核对。

3. **已完成工作：** 助手按[预飞行](../research/ws21-local-heartbeat-preflight.md)在 Luna High 阶段完成 `20260930-020000-ws21hb-k4-unit` 的优化构建、启用测试的 `devices-point-to-point` 单测，随后串行完成 off、200 µs 正常、丢 HELLO、丢 ACK、50 µs 正常、1000 µs 正常六格，编号为 `20260930-020100` 至 `020600` 的原表完整 ID。六格均 `SUCCEEDED`，各 1/1 流和 67,108,864 B 守恒，全部 raw 和资源收据已回传；单测 metadata 为 `BUILT`，资源收据为 `TESTED`，点对点 suite 含反馈/心跳头测试均 `PASS`。50/200/1000 µs 分别完成 112/28/6 次 HELLO/ACK 往返、产生 9,856/2,464/528 B 逐跳控制字节；相对关闭格 5.582475 ms 的 FCT 分别多 336/84/18 ns。两种 200 µs 连续丢失格各注入 19 次，超时 19 次、`UNKNOWN` 1 次、恢复 1 次，检测发生在故障窗口起点后 701.083 µs，窗口结束后 3.168 µs 恢复。分析器同时验证源 SHA、两个输入哈希、seed、配置、业务字节、心跳计数与事件顺序、逐跳队列守恒、日志未溢出和资源限额。

4. **已形成的设计决策：** 用户提出精简报文、局部心跳与时效/代价权衡；助手选择 10 B HELLO/ACK 仅带版本、类型、epoch、序号，让实际入端口给出邻居身份，并只在业务活跃上联订阅。`STATE` 拥塞汇总与心跳独立分账。本轮 `UNKNOWN` 仅供监测。三档周期形成成本与预期检测速度的取舍，200 µs 是实际验证过连续丢失状态收敛的参考点；没有故障恢复 SLO、50/1000 µs 故障试验或多流重复，不选唯一最优周期，也不把控制包丢失冒充物理链路断开。

5. **当前状态（2026-09-30）：** 小拓扑正常往返、连续控制消息丢失后失联/恢复的**技术子门槛已通过**。七个 ID 独立、终态且回传；仿真阶段后已切至 Sol High 做本报告的逐格分析。最大仿真进程树 RSS 880.8 MiB，最低可用内存 122.17 GiB；六格各自仿真墙钟 3–4 s，独立优化构建各约 346–347 s，耗时主要来自构建与测试。个人 fork 分支 `feature/ws21-downstream-feedback` 在报告编辑前 HEAD 为 `2709ca4b34ef4c35b5ac69271b146baefb3164a1`；文档/分析器提交会移动 HEAD，但不改变上述仿真源码 SHA。

6. **未解决问题：** 单份丢失不误报、旧/重复/乱序/跨端口 ACK、重启与显式链路 down/up 尚未定向验证。注入仅丢 HELLO 或 ACK，业务链路未断，故不能推出业务绕路/恢复。单流、一个活跃端口、seed 1 的 52 节点技术 pilot 不代表长尾拓扑的心跳规模与性能。尚无 `STATE+HELLO/ACK` 联合格，反馈缓存未进入选路；`adopted/fallback` 和候选质量区分仍未得到证明，效果矩阵 NO-GO。

7. **后续推荐动作：** 若继续心跳技术路线，先用短故障窗验证单份丢失，再覆盖 ACK 身份、会话重启、链路状态和物理断链；每项固定新 SHA/输入/ID 与停止条件。只有局部故障类别和资源门槛通过后，才用固定长尾输入测活跃上联占比和 `STATE+HELLO/ACK` 联合逐跳成本。选路效果须另证候选可区分、状态先于决策到达和 `adopted/fallback` 生效，并用独立需求和同输入双侧对照；没有业务 SLO 时保留连续成本/时效曲线。

8. **与其他工作流的关系：** 此技术 pilot 与 WS-21 旧 16,576 流 `STATE` 更新间隔矩阵分账；旧矩阵的 10 µs 条件性成本档只针对反馈样本年龄，不等于本心跳的 200 µs 参考周期。WS-10/11/12/19/20 的既有 no-go 不重判；WS-22/23/24 各有独立门槛，WS-25 只整合实际证据。此前[Handoff 37](2026-09-30-37-ws21-local-heartbeat-preflight.md)保留预飞行时状态并已加执行勘误。
