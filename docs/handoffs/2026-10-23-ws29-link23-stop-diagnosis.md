## 3. 已完成工作

固定源码与原日志共同定位了以下调用路径。

1. `scratch/network-load-balance.cc` 仅在端口日志或 heartbeat 开启时填充 `m_ws21HostPorts`。C0 两项均关闭，集合为空。
2. `SwitchNode::Ws29Fault(23, ...)` 依赖该集合排除主机端口。集合为空时，端口 1 被当作交换机间端口处理。
3. 邻居实际为主机，转换成 `SwitchNode` 后得到空指针。optimized 构建移除了 `NS_ASSERT_MSG` 检查。
4. 代码先调用本端 `Ws29LinkState`，打印端口 1 的 down 事件，再通过空邻居指针调用对端方法。日志边界与这条路径一致。

这是源码和原日志支持的定位。只读检查未在该 ID 的源码或结果目录找到 core。远端 `core_pattern` 指向 apport，虽有 gdb，当前没有可读取的运行时 backtrace。未重放崩溃。

远端只读材料保存在 `results/ws29-link23-diagnosis/`。运行后源码目录的 tracked diff 仅有 `mix/.history` 的四行运行记录。该记录保留原状。

## 4. 已形成的设计决策

最小修复提交为 `ec0c718f435a54f684d18e6933583335a60f81d5`，位于 `feature/ws29-downstream-feedback`，尚未推送。

- WS-29 初始化也填充主机端口集合。
- 批量 down/up 按信道对端的真实节点类型选择端口，消除对可选遥测初始化的依赖。
- 物理目标和空交换机邻居使用运行时检查，optimized 构建也会执行。
- 新增 C++ 行为测试：三个臂均关闭遥测，且不填充主机端口集合。测试验证主机链路保持 up，交换机链路两端 down 后均可恢复。

修复涉及各臂共用的故障注入与端口分类。`GetOutDev` 的存活端口筛选、QP 缓存失效、反馈评分、采用规则、预算参数和输入均未改动。C0 的反馈本来就关闭，因此此次崩溃没有提供反馈候选失效的效果证据。

主审确认此次属于工程缺陷修复，不消耗机制候选或机制诊断修正名额。额外构建与验证仍有计算成本。
