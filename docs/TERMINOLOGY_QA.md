<a id="tq-001"></a>
## TQ-001：单 seed 是什么？

**通用含义。**`seed`（随机种子）是随机数生成过程的起点。同一生成程序、同一参数和同一 seed 通常可重现同一随机样本。**单 seed** 指本次比较只使用了一份独立的随机样本；在这份样本上跑多个算法，仍只有一个独立样本。样本内有 320 条流，也不等于有 320 个独立 seed。

**本项目口径。**至少要区分两种 seed：①生成流量 trace 的 seed，决定流量样本；②ns-3 仿真的 `RANDOM_SEED`，影响模拟器内的随机行为。原始 `traffic_gen.py` 没有单独设置 Python 随机种子，所以仅记录 `RANDOM_SEED 1` **不能**证明 trace 可重生；配对比较必须保存完全相同的 trace 文件及 SHA-256。WS-09 的三个 320 流技术 pilot 共用同一份 trace、拓扑、源码 SHA 和仿真 seed，因此能做该样本内的配对核对，但独立 trace 样本数仍为 **1**。输入审计见论文项目根目录 `docs/research/10-baseline-fidelity-and-dataflow-audit.md`；[WS-09 机器摘要](research/ws09-validation-summary.json)记录了本轮配对输入。

**容易误解：**“同一个 seed 跑三种算法”是三次仿真运行，不是三次独立重复。想判断趋势是否稳定，需要预先确定多个独立 trace seed，并让每个 seed 下的算法复用该 seed 的同一份 trace。具体重复判据见 [WS-07 实验契约](research/ws07-dual-track-contract.md)。

<a id="tq-002"></a>
## TQ-002：pilot 是什么？

**通用含义。**`pilot` 是先导试验或试运行。在投入完整实验成本前，它检查输入、实现、测量方法和资源预算是否可行，也可暴露明显失败。它可以给出初步数值，但初步数值不自动成为正式结论。

**本项目口径。**WS-09 的 *technical pilot* 用固定的 256 条 MoE 流加 64 条背景流，在相同 trace 和传输条件下跑 `shortq2`、`guardhash`、`guardhashgate`，检查完成率、双候选/门控是否触发、队列计数守恒及运行耗时。它只用了一个独立 trace 样本，也没有完成固定总字节、多 seed 和正式强对照，因此不能据某一格的 FCT 差值宣布 GuardHash 有效。[WS-09 Handoff](handoffs/2026-09-26-10-ws09-guardhash-prototype.md)记录该 pilot 的实验 ID 与限制。

| 层级 | 主要回答的问题 | 本项目中的例子 |
| --- | --- | --- |
| smoke / fidelity check | 程序与既有基线链路能否跑通？ | 四模式最小 fidelity 运行；不用于性能排名。 |
| technical pilot | 新机制、计数和配对输入能否正确运行？资源大致够不够？ | WS-09 单 seed 三模式试运行。 |
| 正式比较 | 效应是否在预先约定的条件和独立样本上稳定，并优于强对照？ | WS-10 与 WS-11 的现象复核各自完成且 no-go；机制效果比较未启动。 |

**容易误解：**`SUCCEEDED` 只表示一次运行通过了运行器的成功条件；它不等于“研究假设成立”。pilot 的正数值或负数值都应保留，但不能拿来事后挑 seed、调阈值或改主指标。

<a id="tq-003"></a>
## TQ-003：ADR 是什么？

**通用含义。**ADR 是 *Architecture Decision Record*，通常译为“架构决策记录”。它用短文档保存一项重要选择的背景、决定、理由、考虑过的替代方案与后果，让后来的人知道为什么这样做。

**本项目口径。**个人 fork 的 `docs/decisions/ADR-###-*.md` 也记录重要研究流程决策，不限于软件架构。[ADR-006](decisions/ADR-006-conditional-guardhash-selection.md)记录 GuardHash 的条件性筛选门槛；[ADR-007](decisions/ADR-007-guardhash-prototype-before-efficacy.md)记录在效果门槛尚未通过时，先允许做可关闭的工程原型，但正式收益判据不变。

**容易误解：**ADR 的 `Accepted` 表示团队采用了这项**决策**，不表示算法效果已被实验验证。效果证据要另看固定源码、实验 ID、原始数据和正式比较。

<a id="tq-004"></a>
## TQ-004：no-go 决策是什么？

**通用含义。**`go / no-go` 是事先设好的继续或停止门槛。`go` 表示证据达到本阶段规定的条件，可以进入下一阶段；`no-go` 表示至少一项必要条件未达到，本阶段不能按原计划向下一阶段作出相应主张。它是研究或项目推进的判断，不是程序报错，也不等于所有相关想法都被证明无效。

**本项目口径。**WS-10 在运行前规定：五个独立流量样本必须完成全部 30 格和所有流；在四条背景大流档位，至少四个样本显示目标短流受到逐包方案的额外损害，且归一化损害的中位数至少为 5%；背景大流的预设安全指标也要通过。实际 30 格及所有流均完成，背景安全指标通过，但只有 **1/5** 个样本在主档位显示正向额外损害，中位数为 **−1.3947%**。所以本轮是**“预设场景中的跨类损害现象 no-go”**：不能把该场景作为 GuardHash/HarmGate 正式收益评估已经具备的前提，也不能宣称算法收益已得到验证。两条背景大流档位的正向结果是预定的剂量检查，不改变四条档位的主判据。具体阈值见 [WS-10 预注册](research/ws10-fixed-load-prereg-v1.md)，原始 ID、计算和结果见 [正式报告](research/ws10-fixed-load-formal-report.md)及[机器摘要](research/ws10-fixed-load-formal-summary.json)。

**容易误解：**no-go 不表示“网络中不存在热点”“全量流量也一定无影响”或“GuardHash/HarmGate 已被证明无效”。它只约束**这份事前约定的输入、传输条件和判据**。WS-11 后来按另一套全量输入契约独立完成 40 格，MoE 交互虽为正，背景 P99 安全线却越过 5%，因此其复合判据也 no-go；两轮不能合并或互相重判。以后若研究新的场景，仍须另立可核验的设计。[后续路线](project-state/ROADMAP.md)保留了这一边界。

<a id="tq-005"></a>
## TQ-005：尾部完成时间，具体指什么？

**通用含义。**先把一次数据传输称为一条“流”：它可包含许多数据包，并非一个包。若一批流有的很快、有的很慢，“尾部”就是较慢的那一端。“尾部完成时间”不是一个唯一的指标，读到它时要追问：统计对象是一条流、一台源主机的一批流，还是整个任务？看的是较慢的 5%/1%，还是最慢的那一条？

| 常见说法 | 统计对象与算法 | 回答的问题 |
| --- | --- | --- |
| 流 FCT P95/P99 | 将**每条已完成流各自耗时**排序，取第 95/99 百分位 | 较慢的一部分流各要多久？ |
| 最大 FCT | 同一批流里耗时最长的一条 | 最慢的单条流花了多久？ |
| 整批完成时间（本项目 `synthetic_batch_completion_us`） | 最后一条流的**绝对完成时刻**减这批流最早开始时刻；只在输入流全数完成时报告 | 从这批业务开始到全部结束要等多久？ |
| 源批次 P99（`p99_complete_source_batch_us`） | 先算每台源主机自己的最后完成时间，再对这些**源主机批次**取 P99 | 哪些源主机的一批流收尾较慢？ |

**本项目口径。**WS-11 的“背景 P99”是 64/128/192 条背景流的**单流 FCT P99**。原始 192 档下，`fecmp` 为 1411.822 微秒，`dualtrack` 为 1505.747 微秒；它们不是整批背景流全部结束的时间。WS-11 的 MoE 主指标则是 16,384 条 MoE 流的**整批完成时间**：每条都在仿真 2.000 秒开始，等最后一条结束。因为这批流同一时刻启动，本轮该指标数值上等于这一批中的最大 FCT，但统计含义仍与 P99 不同。源码只提供流记录，没有明确的八轮任务边界，所以这个“合成批次”不能写成实测的“八轮 job CCT”。定义见 [按标签分析脚本](../scripts/analyze_moe_tags.py)和 [WS-11 预注册](research/ws11-full-moe-prereg-v1.md)。

**容易误解：**P99 不是“最后一条流”，整批完成时间也不是 P99。即使 99% 的流很快，只要最后一条严重拖延，整批完成时间仍会很长。若有流未完成，仅从已完成流计算 P99 可能显得虚假地快；本项目同时报告输入数、完成数和完成率，并在整批未全数完成时把整批完成时间记为 `null`。

<a id="tq-006"></a>
## TQ-006：FCT 是什么？

**通用含义。**FCT 是 *Flow Completion Time*，即“流完成时间”或“单流完成耗时”：从这条流开始，到这条流按实验定义完成，经历了多久。公式是 **FCT = 完成时刻 − 开始时刻**。例如 2.000 秒开始、2.0015 秒完成，FCT 就是 0.0015 秒 = 1.5 毫秒 = 1500 微秒。它可能包含发送、链路传播、排队、拥塞反馈和重传等时间，不只是数据包在链路上的发送时间。

**本项目口径。**ns-3 在 RDMA 队列对完成回调 `qp_finish` 中写一行原始 FCT，含源/目的、端口、字节数、开始时间、`Simulator::Now() − startTime` 和单独计算的理想无争用时间；原始时间单位为纳秒，分析时换成微秒。WS-11 的[标签分析脚本](../scripts/analyze_moe_tags.py)把每行完成记录与输入 trace 的对应流匹配，再分别统计 MoE (`tag=2`) 与背景 (`tag=1`)。原始生产位置见 [仿真源码](../scratch/network-load-balance.cc)，WS-11 的全类完成与指标见[机器摘要](research/ws11-full-moe-formal-summary.json)。

**相关指标。**平均 FCT 是这些单流耗时的算术平均，最大 FCT 是最慢一条；完成率是已完成流数除以输入流数。旧分析里的 `slowdown`（放慢倍数）是 `max(1, 实际 FCT / 理想无争用 FCT)`：例如理想需 10 微秒、实际需 20 微秒，放慢倍数是 2。它用一个理想时间作参照，既不是 FCT 的时间单位，也不是吞吐量；WS-11 的预注册主判据没有用它替代 MoE 整批完成时间或背景 P99。

**容易误解：**FCT 不是发送时刻、吞吐率，也不是整个 MoE 任务的完成时间；一条 8 MiB 背景流与一条 8 KiB MoE 流的 FCT 不能脱离流大小直接比较优劣。本项目旧 baseline 分析还有 `2.005–2.060` 秒的完成流筛选窗口，它排除了 `2.000` 秒同启的 WS-11 MoE；WS-11 使用输入 trace 为分母的独立按标签分析，不沿用那个旧窗口。旧口径见论文项目的 `docs/research/10-baseline-fidelity-and-dataflow-audit.md`。

<a id="tq-007"></a>
## TQ-007：P95、P99 是什么？

**通用含义。**`P` 是 percentile（百分位数）。先确保样本是同一种东西、同一个单位，再从小到大排列。P50 是中位数；P95 大致是“约 95% 的样本不超过它”的位置，P99 大致是“约 99% 的样本不超过它”的位置。对 FCT 这种“越小越快”的量，P99 变大表示较慢的一端变慢。平均值可能被极端值拉动，P95/P99 则帮助观察分布尾部；最大值看最后一个样本，比 P99 更容易被单个极端值左右。

**本项目口径。**[分析函数](../scripts/analyze_result.py)先排序，再用位置 `(样本数−1)×百分位/100`，落在两条记录之间时做线性插值。因此 P99 不一定恰好等于某条流的 FCT，也不能简单说“就是第 99 条”。例如 100 条流中 99 条都是 10 毫秒，只有一条是 100 毫秒：本函数的 P99 为 **10.9 毫秒**，最大值却是 **100 毫秒**。WS-11 原始 192 档的背景 P99 是对 **192 条背景流**计算的，靠近最慢的两三条，少数尾流变化就可能明显改变它；两模式的 192 条流都已完成。[WS-11 正式报告](research/ws11-full-moe-formal-report.md)中 6.653% 是 `dualtrack` 相对同输入 `fecmp` 的背景 P99 **相对增幅**，不是绝对故障率。

同一批背景流的几个数放在一起，更容易看出“典型流”与“尾流”的区别（单位均为微秒）：

| WS-11 原始 192 档 | P50 | P95 | P99 |
| --- | ---: | ---: | ---: |
| `fecmp` | 738.479 | 1368.906 | 1411.822 |
| `dualtrack` | 756.997 | 1398.403 | 1505.747 |

**容易误解：**“P99 为 1505 微秒”不表示所有流都在 1505 微秒内完成，也不表示有 99% 的时间网络处于该延迟。它描述的是这批**流的完成耗时分布**。比较两个 P99 前，应确认类别、流大小、样本数、输入、完成率、单位和百分位计算方法一致；若有未完成流，已完成样本的 P99 不能单独代表全部输入。

<a id="tq-008"></a>
## TQ-008：CDF 是什么？

**通用含义。**CDF 是 *Cumulative Distribution Function*，累计分布函数。横轴若是 FCT 时间，纵轴在时间 `x` 处表示“样本中有多少比例的流，其 FCT **不超过 x**”。例如 100 条流中 80 条在 1 毫秒内完成，则 `CDF(1 毫秒)=80%`；若 96 条在 2 毫秒内完成，则 `CDF(2 毫秒)=96%`。把每个时间门槛的比例连起来，就看到整段从快到慢的分布，而 P95/P99 只是从中抽取两个位置。有限样本形成阶梯状的经验 CDF；图形软件可能把点连成线。

**本项目口径。**老的 `fctAnalysis.py` 可输出 FCT 与 slowdown 的 CDF；`analysis/plot_uplink.py` 也能画上联链路不均衡的 CDF。因此读图必须先看**横轴是什么量、统计对象是什么、单位是什么**：FCT CDF、slowdown CDF 和链路不均衡 CDF 不是同一个指标。对同一输入的 FCT CDF，在相同时间 `x` 下曲线越高，表示更多流已在 `x` 内完成；在相同百分位下对应时间越靠左，表示越快。两曲线可能交叉，此时不能只凭一处高低说某方案全面更优。WS-11 的正式结论来自按标签核对的完成率、MoE 整批时间和背景 P99，并非只看一张 CDF 图。

**容易误解：**CDF 的纵轴是**累计比例**，不是“恰好在 x 时刻完成的比例”；P99 是从分布读出的一个尾部摘要，不等于最大值。绘图前若只保留已完成流，曲线最终仍可能到 100%，却掩盖未完成输入，所以还必须同时报告“完成了多少条／原本有多少条”。

新增用户术语问题时，保留其原问题措辞，追加下一个 `TQ-###`，同时更新顶部索引。每条优先写“通用含义—本项目口径—容易误解”，并链接具体源码、实验或 ADR；证据未完成时明确写“待验证”，不把术语解释写成性能结论。
